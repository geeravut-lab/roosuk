# e-KYC และ Telepharmacy — การออกแบบ และสิ่งที่คนต้องตัดสินใจ

> ต้นทางความรู้: `SkillConnect_eKYC_Skill.md` (e-KYC) และ `KNOWLEDGE_telepharmacy.md` (ปรึกษาเภสัชกร)
> แปลงมาใช้กับ stack ของ RooSuk (Next.js + Supabase) · สัญลักษณ์ 🔒 = ต้องให้คน (เจ้าของ / เภสัชกรผู้รับอนุญาต / ที่ปรึกษากฎหมาย) ตัดสินใจก่อนเปิดใช้กับผู้ใช้จริง
> สถานะ: เขียนโค้ดและทดสอบด้วยตัวจำลองแล้ว · **ยังไม่เคยเรียก iApp จริง และยังไม่ได้ apply migration กับ Supabase** (ดู §9)

## 1. ภาพรวม

```
ผู้ใช้ ──/verify──▶ e-KYC (liveness → OCR บัตร/พาสปอร์ต → เทียบใบหน้า) ──▶ ekyc_verifications (ข้อมูลที่ปิดบังแล้ว + คะแนน, ไม่มีรูป)
   │                                    │ ไม่ผ่าน → คิว /admin/ekyc (อนุมัติ/ไม่อนุมัติ + audit)
   │                                    ▼
   │                         is_kyc_verified(uid)  ◀── ใช้ที่ 3 จุด
   │                                    │
   ├─ /telepharmacy (ขอปรึกษา/จองเวลา) ◀┤ (1) ผู้ขอปรึกษา  (2) เภสัชกรก่อนรับสาย
   └─ ตะกร้าสินค้า create_shop_order ◀──┘ (3) สินค้าที่ติด requires_kyc
```

หลักการที่ทุกส่วนยึด: **ฝั่งเซิร์ฟเวอร์ตัดสินทุกอย่าง** (ผู้ใช้ส่งได้แค่รูป/ฟอร์ม) · สถานะเปลี่ยนผ่านฟังก์ชัน SQL แบบ SECURITY DEFINER ที่ล็อกแถว · ผู้ใช้ไม่มีสิทธิ์เขียนผลยืนยัน/สถานะการปรึกษาเอง · ไม่เก็บรูป · ข้อความที่ออกนอกแอปไม่มีรายละเอียดสุขภาพ

## 2. e-KYC

| เรื่อง              | การทำงาน                                                                                                                                                                                                                                                         |
| ------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| ผู้ให้บริการ        | `src/lib/ekyc/iapp.ts` (iApp Technology, `apikey` header, multipart, `file`/`file1`+`file2`, ลอง path พาสปอร์ตตามลำดับ) · คีย์ `IAPP_API_KEY` อยู่ที่เซิร์ฟเวอร์เท่านั้น · ตัวจำลอง `test-double.ts` ใช้ใน unit test เท่านั้น (มี test กันไม่ให้โค้ดจริง import) |
| ไม่มีคีย์ / ปิดอยู่ | หน้า `/verify` แสดง "บริการยังไม่เปิด" · ไม่มีทางผ่านโดยไม่ตรวจจริง                                                                                                                                                                                              |
| การตัดสิน           | `decide()` ผ่านเมื่อ **ทุกขั้นที่แอดมินเปิดอยู่** ผ่าน · ขั้นที่ปิดถูกข้าม · คะแนน liveness/face เทียบกับเกณฑ์ที่แอดมินตั้ง                                                                                                                                      |
| ข้อมูลที่เก็บ       | `ekyc_verifications`: ชื่อจาก OCR, เลขเอกสารปิดบัง (เห็น 4 ตัวท้าย), คะแนน, ขั้นที่ผ่าน/ไม่ผ่าน, เวลา — **ไม่มีรูป ไม่มีเลขเต็ม**                                                                                                                                |
| ขีดจำกัด            | ≤ 2 MB ต่อรูป (ตรวจชนิดจาก bytes) · ส่งได้ N ครั้ง/วัน/คน (ค่าเริ่ม 5, แอดมินปรับ) · ผู้ที่ยืนยันแล้ว **ส่งซ้ำไม่ได้** · มีเคสรอตรวจอยู่ก็ส่งซ้ำไม่ได้ — ตัดสินใน SQL (`ekyc_begin_attempt`) ภายใต้ล็อกต่อผู้ใช้                                                 |
| ไม่ผ่าน             | เข้าคิว `/admin/ekyc` → อนุมัติ/ไม่อนุมัติ (บันทึกใน `privacy_audit_log` + แจ้งผู้ใช้) · ไม่มีการปฏิเสธถาวรโดยอัตโนมัติ                                                                                                                                          |
| แอดมิน              | `/admin/ekyc`: สวิตช์, ชนิดเอกสาร, เปิด/ปิด liveness และ face match, เกณฑ์, จำนวนครั้ง/วัน, คิวตรวจ, เพิกถอน, รีเซ็ตตัวนับ (ตามอีเมลผู้ใช้)                                                                                                                      |
| ฝั่งผู้ใช้          | `getUserMedia` ถ่าย selfie สด (ถ้าเปิดกล้องไม่ได้ จึงให้เลือกไฟล์) · ย่อรูปเป็น JPEG ตามบทที่ 5.2 ของ blueprint (ย่อระหว่าง decode, ปล่อย canvas/bitmap ทันที, selfie ก่อนเอกสาร) · ต้องติ๊กยินยอม                                                               |
| ตัวช่วย             | `isKycVerified(userId)` · `requireKyc(userId)` (โยน `err_kyc_required`) ใน `src/lib/ekyc/server.ts` · ใน SQL: `is_kyc_verified(uuid)`                                                                                                                            |

### e-KYC ใช้ที่ไหน

1. **Telepharmacy — ผู้ขอปรึกษา:** เมื่อ `require_kyc_for_consult` เปิด (ค่าเริ่ม **เปิด**) · ตรวจทั้งใน TypeScript และในฟังก์ชัน SQL ที่สร้างการปรึกษา
2. **Telepharmacy — เภสัชกร:** `require_kyc_for_pharmacist` (ค่าเริ่ม **เปิด**) · เภสัชกรกดพร้อมรับสาย/รับสายไม่ได้ถ้ายังไม่ยืนยันตัวตนหรือใบอนุญาตยังไม่ถูกยืนยัน
3. **ซื้อสินค้า:** สินค้าที่ติ๊ก "ต้องยืนยันตัวตน" (`shop_products.requires_kyc`) · บังคับ **ในฟังก์ชัน `create_shop_order`** (ไม่มีทางอ้อมจากโค้ดฝั่งแอป) · ถ้า e-KYC ปิดอยู่ สินค้านั้นจะซื้อไม่ได้ (ปลอดภัยไว้ก่อน)

## 3. Telepharmacy

### ตาราง (migration `20261115000300_telepharmacy.sql`)

| ตาราง                        | หน้าที่                                                                                                                                                                                                         | ใครเขียน              |
| ---------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------- |
| `telepharmacy_settings`      | แถวเดียว: เปิด/ปิด, ชั่วโมงให้บริการ, ช่วงนัด, timeout, คิวสูงสุด, สายสูงสุด, ผู้ให้บริการวิดีโอ, เวอร์ชัน/ข้อความยินยอมและคำเตือน (th/en), บังคับ e-KYC, retention                                             | แอดมิน (service role) |
| `pharmacists`                | บัญชีเภสัชกร: ชื่อ, เลขใบอนุญาต, `license_verified` (**ตั้งได้ผ่านฟังก์ชัน `admin_set_license_verified` เท่านั้น**), online/last_seen/active_consult_id                                                         | แอดมิน/เซิร์ฟเวอร์    |
| `consults`                   | การปรึกษา (instant/scheduled), สถานะ `waiting/booked/accepted/done/missed/cancelled`, ห้องวิดีโอ (ชื่อสุ่ม), hash ของ access key, เวอร์ชัน+hash ของข้อความยินยอม, สิ่งที่ผู้ใช้เลือกแชร์ (snapshot)             | ฟังก์ชัน SQL เท่านั้น |
| `consult_records`            | บันทึกการให้บริการ (เขียนโดยเภสัชกร): เวลา, ประวัติผู้ป่วย (สำเนาที่ยินยอมแชร์), คำแนะนำ, แนะนำพบแพทย์?, ผลิตภัณฑ์ที่ **เภสัชกรเลือก**, นัดติดตามผล/ผลติดตาม · ยืนยันแล้วแก้ไม่ได้ (trigger) ยกเว้นส่วนติดตามผล | เซิร์ฟเวอร์           |
| `consult_access_log`         | ใครเปิดบันทึก/ข้อมูลแชร์ของใคร เมื่อไร — **append-only** (trigger ห้ามแก้/ลบ/truncate แม้ service role) · ผู้ใช้ดูของตัวเองได้ในหน้า `/telepharmacy`                                                            | ฟังก์ชัน SQL          |
| `telepharmacy_consent_texts` | ข้อความยินยอมที่ผู้ใช้เห็นจริง เก็บตาม hash ถาวร (ไม่มีวันแก้)                                                                                                                                                  | เซิร์ฟเวอร์           |

### การทำงาน

- **โหมด B (คุยตอนนี้):** เภสัชกรเปิดสวิตช์ในหน้า `/pharmacist` → ส่ง heartbeat ทุก 45 วินาที (ใช้นาฬิกาเซิร์ฟเวอร์) · "ว่าง" = online + heartbeat ภายใน 120 วินาที + ไม่มีสายอยู่ + ใบอนุญาตยืนยันแล้ว (+ e-KYC ถ้าบังคับ) + อยู่ในเวลาให้บริการ — คำนวณใน SQL · ผู้ใช้ขอ → `waiting` → เภสัชกรกดรับ (`claim_consult` ล็อกแถว, 1 สายต่อเภสัชกรด้วย unique index) → `accepted` → จบสาย → `done` · ไม่มีคนรับเกิน `wait_timeout_sec` → `missed` (sweep)
- **โหมด A (จองเวลา):** ช่วงนัดคำนวณจากชั่วโมงให้บริการ · `book_consult_slot` ล็อกต่อช่วงเวลา + unique index `(scheduled_at, slot_no)` จึง **จองซ้ำช่องเดียวกันไม่ได้** · เตือนผู้ใช้ก่อนนัด · เภสัชกรเริ่มได้ตั้งแต่ 15 นาทีก่อนนัด
- **Sweep:** `sweep_consults` ถูกเรียกจาก tick ตามเวลา (`/api/cron/notify` ผ่านขั้น `consult_sweep` และ `consult_reminders`) **และ** ทุกครั้งที่เปิดคิว/ถามสถานะ (เพราะ tick ทุก 10 นาที แต่การรอวัดเป็นนาที)
- **วิดีโอ:** `makeRoom` (ชื่อห้องจาก `crypto.randomBytes`) · ลิงก์สร้างตอนที่ "สองฝ่าย" ขอเท่านั้น ไม่เก็บ ไม่ส่งทางแจ้งเตือน · access key ของผู้ใช้เก็บเฉพาะ SHA-256 เทียบด้วย `timingSafeEqual` · ผู้ให้บริการ `jitsi` (ค่าเริ่ม) / `jaas` (JWT RS256 ผู้เภสัชกรเป็น moderator, ปิด recording) / `custom`
- **การแจ้งเตือน** (`notifyUser`): "มีผู้รอปรึกษา" → เภสัชกรที่ว่าง · เตือนนัด · สายที่ไม่มีผู้รับ · ถึงวันติดตามผล — **ไม่มีอาการ/ยา/ผลิตภัณฑ์/หัวข้อ** ในข้อความ (มี test)
- **ผลิตภัณฑ์:** เภสัชกรเป็นผู้เลือกใส่ในบันทึกเอง ระบบไม่เสนอยาอัตโนมัติ ไม่มีขนาดยา · ปุ่ม "ปรึกษาเภสัชกร" ที่หน้าสินค้าส่ง `?product=<id>` มาเป็นบริบท

### ตอบข้อกำหนด 8.1–8.3 ของเจ้าของ

| ข้อ                                 | ทำอย่างไร                                                                                                                                                                                                                                                                                                                                      |
| ----------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 8.1 บันทึกตามสภาเภสัชกรรม           | `consult_records`: วัน-เวลาและระยะเวลาให้บริการ, ประวัติผู้ป่วย (ข้อมูลที่พิมพ์ + สำเนาโปรไฟล์/ผลตรวจ/บันทึกครั้งก่อนที่ผู้ใช้ยินยอมแชร์), ข้อมูลบริการ (คำแนะนำ, ส่งต่อแพทย์, ผลิตภัณฑ์ที่แนะนำ), ติดตามผลการใช้ยา (วันนัด, คำตอบผู้ใช้, ผลที่เภสัชกรบันทึก) · 🔒 รายการฟิลด์ต้องให้เภสัชกรผู้รับอนุญาตเทียบกับประกาศสภาเภสัชกรรมฉบับปัจจุบัน |
| 8.2 ยืนยันตัวตนทั้งสองฝ่าย + ยินยอม | ผู้ขอ: e-KYC · เภสัชกร: e-KYC **และ** ใบอนุญาตที่แอดมินตรวจกับต้นทางแล้ว (ระบบไม่ยืนยันให้เอง; แก้เลขแล้วการยืนยันหายอัตโนมัติ) · ความยินยอม: 2 ข้อบังคับ (ปรึกษาทางวิดีโอ / จัดทำบันทึก) + 3 ข้อเลือกได้ (แชร์โปรไฟล์ / ผลตรวจ / บันทึกครั้งก่อน) · เก็บเวอร์ชัน+hash+ข้อความจริง                                                             |
| 8.3 เก็บปลอดภัย ตรวจย้อนได้         | RLS ทุกตาราง · เภสัชกรอ่าน snapshot/ที่ผู้ใช้พิมพ์ผ่านเซิร์ฟเวอร์เท่านั้น (ไม่มีสิทธิ์อ่านคอลัมน์เหล่านั้นจาก client) และทุกครั้งที่เปิดถูกจดใน `consult_access_log` · ผู้ใช้ตรวจดูได้ว่าใครเปิด · บันทึกที่ยืนยันแล้วแก้ไม่ได้ · ข้อมูลอยู่ใน Supabase เดียวกับข้อมูลสุขภาพอื่น (ภูมิภาคตาม `src/config/data-region.ts`)                      |

## 4. PDPA: ส่งออก / ลบบัญชี

เพิ่มใน `src/config/user-data.ts`:

- `ekyc_verifications`, `ekyc_attempts`, `pharmacists` → **ลบพร้อมบัญชี**
- `consults`, `consult_records`, `consult_access_log` → **เก็บไว้แต่ตัดตัวตน** (เหมือนใบสั่งซื้อ): ชื่อผู้ใช้, สิ่งที่พิมพ์, snapshot, สำเนาประวัติในบันทึก ถูกล้างโดย trigger · คำแนะนำของเภสัชกรและชื่อ/เลขใบอนุญาตของเภสัชกรอยู่ต่อ · ส่งออกข้อมูลของผู้ใช้รวมตารางเหล่านี้ (ยกเว้นชื่อห้อง/hash ที่ไม่ใช่ข้อมูลของเขา)
- 🔒 **ต้องให้ที่ปรึกษากฎหมายตัดสิน:** บันทึกการให้บริการเภสัชกรรมต้องเก็บตามกฎหมายหรือไม่ นานเท่าไร และเมื่อผู้ใช้ขอลบบัญชีควร "เก็บแบบตัดตัวตน" (ที่ทำไว้) "ลบทั้งหมด" หรือ "เก็บทั้งหมดจนครบกำหนด"

## 5. สิ่งที่เจ้าของ/กฎหมาย/เภสัชกรต้องตัดสินใจ 🔒

1. **ข้อความยินยอม PDPA และคำเตือนทางการแพทย์** (ไทย/อังกฤษ) — ระบบมี "ฉบับร่าง" ให้แสดงเมื่อแอดมินปล่อยว่าง · ต้องให้เภสัชกรผู้รับอนุญาต + ที่ปรึกษากฎหมายเขียน/ตรวจ ก่อนเปิดบริการ · แก้ข้อความต้องเปลี่ยนป้ายเวอร์ชัน (ระบบบังคับ)
2. **กฎสภาเภสัชกรรม/กฎหมายเภสัชกรรมทางไกล** — ใครให้คำปรึกษาได้, ต้องมีใบอนุญาตอะไร, ข้อห้ามเรื่องยาควบคุม, ฟิลด์บังคับในบันทึก, ต้องมีเภสัชกรผู้มีหน้าที่ปฏิบัติการประจำหรือไม่ — เอกสารนี้ไม่ยืนยันข้อกฎหมายใดๆ
3. **การตรวจใบอนุญาต** — แอดมินต้องตรวจกับต้นทาง (สภาเภสัชกรรม) แล้วกดยืนยันเอง · กำหนดความถี่ตรวจซ้ำ (ใบอนุญาตหมดอายุ/พักใช้)
4. **ระยะเก็บข้อมูล** — ค่าเริ่ม 1,825 วัน (5 ปี) เป็นเพียงค่าตั้งต้น · ระบบ **ไม่ลบเอง** แอดมินกดลบเองพร้อมพิมพ์ยืนยันและมี log · รวมถึงนโยบายเก็บ `ekyc_verifications` (ชื่อ+เลขปิดบัง) และ `consult_access_log`
5. **ผู้ให้บริการและข้อมูลข้ามประเทศ** — iApp (รูปบัตร/ใบหน้าถูกส่งไปตรวจที่ผู้ให้บริการ: ต้องมีสัญญาประมวลผลข้อมูล, ที่ตั้งข้อมูล, ไม่เก็บรูปหรือไม่) · Jitsi สาธารณะ (`meet.jit.si`) ไม่มี SLA/ควบคุมห้อง → ใช้ทดลองเท่านั้น ก่อนใช้กับผู้ป่วยจริงเลือก JaaS หรือโฮสต์เอง
6. **ใครเปิดดูบันทึกได้บ้าง** — ตอนนี้: เภสัชกรเจ้าของสายและผู้ป่วยเท่านั้น (แอดมินเห็นเฉพาะสถิติ/CSV ที่ไม่มีตัวตนผู้ป่วย) · ถ้าต้องให้แอดมิน/ผู้ตรวจสอบเปิดดูเนื้อหา ต้องกำหนดสิทธิ์และให้บันทึกใน access log
7. **ค่าบริการปรึกษา** (ถ้าจะเก็บ) — ยังไม่ทำ · ยอด/เงื่อนไขคืนเงินต้องให้เจ้าของอนุมัติ
8. **เกณฑ์ e-KYC** — ค่าเริ่ม liveness 0.8, face 0 (ใช้ค่าของผู้ให้บริการ) · เหมาะสมกับความเสี่ยงของสินค้า/บริการหรือไม่ · ตรวจวันหมดอายุบัตร/เทียบชื่อกับโปรไฟล์ (blueprint ข้อ 11.5) ยังไม่ได้ทำ
9. **ผลิตภัณฑ์ที่ต้องยืนยันตัวตน** — เจ้าของเลือกเองว่าสินค้าใดติด `requires_kyc` (ยาควบคุม/ผลิตภัณฑ์เฉพาะ)

## 6. สิ่งที่ทำไม่ได้ในสภาพแวดล้อมนี้ / ข้อจำกัด

- ไม่มี `IAPP_API_KEY` → ไม่เคยทดสอบกับ iApp จริง (ตอบกลับของผู้ให้บริการทดสอบด้วย fetch จำลอง) · ต้องทดสอบจริง: บัตรไทย/พาสปอร์ต, Android/iOS, กล้องหน้า, รูปมัว (ต้องได้ข้อความ "ไม่พบเอกสาร")
- ไม่มีกล้อง/วิดีโอจริง → ห้อง Jitsi/JaaS ไม่เคยเปิดจริง · ต้องทดสอบ 2 อุปกรณ์ (เภสัชกรเข้าห้องก่อนได้ไหม, moderator)
- Netlify tick รันทุก 10 นาที → การเตือนนัดมีความละเอียด ~10 นาที (การปิดสายที่รอเกินเวลาไม่พึ่ง tick เพราะเรียก sweep ทุกครั้งที่อ่านคิว) · ถ้าต้องการเตือนละเอียดขึ้นให้ปรับ schedule ของ `netlify/functions/notify-tick.mts`
- การแจ้งเตือนเภสัชกรเมื่อมีผู้รอ ใช้ in-app + LINE (ถ้าเชื่อมไว้) ยังไม่มีเสียง/Web Push เด้งเตือนในหน้า `/pharmacist` (หน้ารีเฟรชคิวทุก 5 วินาทีขณะเปิดสวิตช์)
- ยังไม่มีการเก็บไฟล์/รูปในการปรึกษา · ไม่มีแชตข้อความในห้อง (ใช้ห้องวิดีโอของผู้ให้บริการ) · ไม่มีการบันทึกภาพ/เสียง
- migration ยังไม่ถูก apply (token Management API ใช้ไม่ได้ขณะพัฒนา) — ทดสอบแล้วบน PGlite เท่านั้น
